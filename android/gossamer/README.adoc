toc::[]

== What this is

Gossamer is the estate's Tauri/Electron alternative (a linearly-typed webview
shell; native core `libgossamer.so` built from Zig FFI + an Idris2 ABI). This
directory stands up the *minimal* Android scaffold so later sub-PRs can port the
legacy Kotlin components. It does **not** change any existing crate or the
legacy `android/app/` Kotlin tree (that tree is removed in a later sub-PR once
the port is complete).

== gossamer-rs resolvability outcome

`gossamer-rs` (v0.1.0) is **not published to crates.io**. In the estate it is
consumed as a *path dependency* from the sibling `hyperpolymath/gossamer` repo at
`bindings/rust` — precedent in `hyperpolymath/panll`:

[source,toml]
----
gossamer-rs = { path = "../gossamer/bindings/rust" }
----

That sibling checkout does not exist in a neurophone clone, so wiring it as a
hard dependency would break `cargo build --workspace`. Per the sub-PR's hard
constraint (CI green > "complete" dep), it is left commented out with a
`TODO(#83 sub-PR #8)` until the gossamer Android build wiring lands. The
`android/gossamer/Cargo.toml` manifest is also kept **out** of the root
workspace `members` (and carries an empty `[workspace]` table) so neither
`cargo build --workspace` nor `cargo test --workspace` ever touches it.

NOTE: The upstream `gossamer-rs` crate is licensed `AGPL-3.0-or-later`; every
file added here is `MPL-2.0`. Whether the cdylib that links `gossamer-rs` can
remain MPL-2.0 or must adopt a compatible license is an *open licensing
question* to resolve before sub-PR #8 enables the dependency.

== GossamerActivity API assumptions

Read from `hyperpolymath/gossamer` `android/src/main/java/io/gossamer/`:

* `io.gossamer.GossamerActivity extends android.app.Activity`.
* Loads `libgossamer.so` via `System.loadLibrary("gossamer")` in a static block.
* `onCreate()` builds a full-screen `WebView`, enables JS + DOM storage,
  *disables* `file://`/content access, registers the `GossamerBridge`
  JavaScript interface (`window.GossamerBridge.postMessage(json)`), and calls
  the native `nativeInit(activity, webview)`.
* Content is supplied by overriding **`getInitialHtml()`** (returns an HTML
  `String`) or **`getInitialUrl()`** (returns a URL `String`); `getInitialHtml()`
  takes precedence. We override `getInitialHtml()`.
* Gossamer on Android is *webview-only today* — no native-widget path.

Assumption: the gossamer Android sources are vendored/linked into the app module
at build time (sub-PR #8), so `io.gossamer.GossamerActivity` is on the
classpath. Until then this shim does not compile/build in isolation and is not
part of any CI build step.

== Explicitly OUT of scope (later sub-PRs)

* `NativeLib` JNI bindings (11 methods) -> *sub-PR #4*. They will be dispatched
  over the Gossamer IPC bridge into the Rust core (`crates/neurophone-core`,
  `crates/neurophone-android`), not called from the Activity.
* `NeurophoneService` foreground sensor loop -> *sub-PR #5*.
* `BootReceiver` -> *sub-PR #6*.
* Home-screen widgets -> *sub-PR #7*.
* Real frontend bundle + full IPC command wiring + enabling `gossamer-rs`
  -> *sub-PR #8*.
* Removal of the legacy Kotlin `android/app/` tree -> after the port completes.

== Risks / open questions

* *Licensing*: MPL-2.0 vs the AGPL-3.0 `gossamer-rs` binding (above).
* *Build integration*: how the gossamer Android sources + `libgossamer.so` are
  vendored into the app module and which build system drives the APK
  (`gossamer` CLI vs Gradle) is undecided; deferred to sub-PR #8.
* *IPC contract*: the mapping from the 11 `NativeLib` methods to Gossamer IPC
  command names/payloads is not yet defined; deferred to sub-PR #4.
